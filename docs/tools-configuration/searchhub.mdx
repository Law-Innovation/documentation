Typical processing purposes: Improve the service

> This guide explains how to reflect searchHub's searchCollector in the Consenter Manager. searchHub does not publish configurable privacy settings, so this guide uses a single fixed-behaviour table.
>
> 1. Implement the service as described below.
> 2. Map the implementation in the Consenter Manager.
> 3. Update your privacy policy to reflect the actual implementation.
>
> The mapping is an example, not a guarantee of legal compliance. Verify it against your implementation and current provider documentation.

## At a glance

**Scope.** searchHub's searchCollector, the tracking component for on-site search journeys [S1]. Sources were checked on 16 November 2026.

**What the service does in this scope.** searchCollector captures anonymised customer search journeys to power the searchHub platform [S1]. According to the provider, the tracking focuses on anonymised search processes and needs no personal data [S2].

> ⚠ **Research gap.** searchHub does not publish which browser storage or identifiers searchCollector uses. "Anonymised" processing can still involve device access under § 25 TDDDG. Load searchCollector after Consenter consent and inspect it in the browser before finalising the mapping.

| Configuration area | Fixed behaviour / required action |

## Step 2 — Map the configuration in the Consenter Manager

| Consenter Manager field | Value to select | Basis and conditions |
|---|---|---|
| Processing purposes | Improve the service | [S1] |
| Tracking method | First party tracking (single session) | Search journeys; verify |
| Identifier | No identifier | Stated as anonymised [S2]; verify |
| Data categories | Browsing and interaction data, Aggregated site statistics | Search journeys [S1] |
| Legal role of data recipient | Processor | Provider on behalf of the shop |
| Personalisation model | No personalisation | — |
| Maximum storage duration | Not documented | — |
| Processing location | Per DPA | Check for US sub-processors |
